## 1. 界面与产品结论（冻结）

- 极简 WLED 式单页，一处醒目的「连接设备并安装」主按钮。
- 「素纸朱印」、现代黑体；背景 #F7F5EF、文字 #292924、朱色 #A74539。不得因为技术接入重新设计成仪表盘或卡片堆。
- 定位「无打扰口袋中文写作」；Slogan「开源，无网络，无 AI，无广告」。
- 保留中英切换、两个说明入口「什么是草稿机」「什么是大鹅输入法」、安装帮助、高级选项、GitHub。
- 微雪 ESP32-S3-RLCD-4.2 为唯一可安装板型。预留的 ST7306 选项继续显示为不可用；**同为 ESP32-S3 不意味着兼容，不得依据芯片族自动判断 PCB 型号**。
- Hero 图片位置已经预留，没有用户批准的实物照片时继续使用黑体「草稿机」回退；不使用其他硬件照片冒充。
- 对外**统一**「连接设备并安装」入口，内部允许对「兼容更新」「全新空板」「不兼容/未知状态」分流；不能为了减少一步用户选择而省去必要备份、擦除确认与拒绝。

## 2. 本轮要实现的真实工作

在隔离分支（建议 `feature/web-installer-r1`）实现可复现静态网站 `web-installer/`，不改输入法核心或固件运行代码。允许将单个 HTML 整理为清晰的少量本地模块，但外观、内容层级和单主操作保持。

**A. 发行资产接线。**
- 固件和安装代码使用明确版本锁定；验证源发布清单、四份 bin 的大小与 SHA-256、ESP 镜像头、App 容量、分区表固定字节。
- 不允许从 `latest` 随意挑资产，不允许上网动态猜固件类型，不允许在用户浏览器中用未校验二进制执行写入。
- 产出自托管的站点构建目录，固件 manifest 和 JS/CSS/二进制依赖的完整交付可一起复制到其他静态托管。测试站不得自动依赖 GitHub API、unpkg/CDN 作为运行条件。

**B. 浏览器连接与只读检查。**
- 优先评估 ESP Web Tools；它能提供 Web Serial 和基础刷写 UI，但**默认新安装可全片擦除**，且通常只按 ESP32-S3 芯片族选镜像。要检验它能否在写入之前完整实现本产品要求的只读设备检查、分区/OTA 判断、指定 App 槽位和独立校验。
- 如果原组件不能无损满足，使用 Espressif `esptool-js` 或同源的受控扩展完成定制流程；不准以「先刷后检查」「永远写 0x10000」替代安全兼容检查。
- 发行 Python 安装器采用 `--no-stub --before no-reset --after no-reset`，原因是当前 USB Serial/JTAG stub 读取在验收现场不可靠。**浏览器端能否在同目标获得等价且可靠的只读数据和校验，属于第一项硬可行性门槛。** 若不成立，明确输出阻碍和替代接入边界；不得暗自移除读取或校验步骤。
- 网页不收集或上传 MAC、Flash 备份、NVS、配对凭据、TF 文稿或学习记录。设备信息只限本地对照及必要的暂时显示。

**C. 兼容更新：优先、默认、必须非破坏性。**
- 按发行 Python 安装器的行为核对目标：ESP32-S3、16 MiB Flash、已知且不启用 Secure Boot/Flash Encryption 的状态、实物微雪型号人工确认。
- 读取并比对实际 `0x8000` 分区表与发行固定 B 分区表；读取 `0xe000` 起 0x2000 的 OTA 数据，并按现有 `check_install.py` 的规则找出唯一支持的活动槽。Pending/rollback/模糊状态一律 STOP。
- 兼容更新**只写活动 App**：slot0 为 `0x10000`；slot1 为 `0x410000`。写入前做只读计划，App 完整长度 <= `0x400000`；写入后进行实际内容的独立校验。
- 更新**不得**执行 `erase-all`、不得写入 bootloader/partition/otadata/NVS/配对区域、不得格式化 TF；不允许用户选择未知槽位强刷。
- 设备校验失败、断线或读写错误：停止、保留状态，不自动擦除、不自动试另一模式、不自动重试、不能虚报安装完成。

**D. 全新安装：同一入口，但有单独安全门槛。**
- 此发行包的全新安装需要将四份文件部署在**本项目实测清单**指定位置：bootloader `0x0`，partitions `0x8000`，boot_app0 `0xe000`，App `0x10000`；并且完整擦除内部 Flash，清除旧设置与配对。
- 正式发行目前只有 fresh 软件夹具验证，**没有全新空板实机首装通过记录**；本轮可以做浏览器软件模拟与明确的中断/回执模型，但不允许直接在现有生产设备上验证 fresh。
- 只有真正证明空白或明确可安全进行 fresh、并取得用户对**全片内部 Flash 清除**的单独确认以及可恢复备份确认后，未来实机阶段才可启用。**遇到未知或不兼容的旧状态，不自动改走 fresh。**
- 额外确认 TF 卡词库、字体及 LearningIndex 均是独立准备步骤，浏览器成功写固件≠整机已具备全部写作资源。网页安装帮助须说明，不能隐去。

## 3. 验证矩阵与退出条件

使用 mock Web Serial/Flash 和真实发行文件构建软件对照。必须覆盖：

| 场景 | 预期 |
|---|---|
| 微雪，16 MiB，固定分区，OTA app0 | 只读检查通过；计划只针对 app0 |
| 微雪，固定分区，OTA app1 | 只读检查通过；计划只针对 app1 |
| 分区表不符／OTA pending 或 rollback | 拒绝写入，状态 STOP |
| 芯片族相同但未确认是微雪板 | 拒绝直接下发固件 |
| 16 MiB 不符／安全信息未知／文件 SHA 不符 | 拒绝 |
| 下载或连接中断、写后不一致 | 停止、明确报告；不得回退为清空重刷 |
| 任意兼容更新路径 | 从不使用全片擦除，从不写非 App 范围 |
| fresh 路径 | 必须另有备份和擦除确认；不通过真实设备执行 |
| 静态网页 | 中英说明/页面布局/非 WebSerial 浏览器反馈正确 |
| TF 资源未备好 | 提供清晰后续指导，不宣称完整可写 |

在软件环境中完成不依赖板子的自动测试，并输出准确测试结果。无法模拟的真实硬件行为如实标为 `DEVICE_PENDING`，不可写成通过。

## 4. 必须交回的成果

1. 可在本地 HTTPS/localhost 预览的静态网站源码、构建/运行说明、锁定版本的依赖以及完整站点发布包。
2. **完整、可审阅的只读兼容性/安装计划**，明确在各状态下是否可写、写哪些偏移、哪些绝不写。
3. 固件来源与完整性验证结果；浏览器连接/读写能力边界，特别说明 stub/no-stub 与 OTA 数据读取是否真实可行。
4. 模拟器/测试夹具及对应回归结果；安装中断和数据保护负例。
5. 简短 `NEXT_DEVICE_TEST.md`：需要在微雪测试设备上执行的**一套连续动作**、事前备份、预期结果及失败停止条件；不拆成多轮逐步人工审批。
6. 一份明确结论：`SOFTWARE_READY_FOR_DEVICE_TEST` 或 `BLOCKED_BY_BROWSER_CAPABILITY`（说明最小阻碍和可行替代），而不是「建议再调研」式空泛回复。

## 5. 授权边界

**本轮不执行任何真实 Flash 写入、全片擦除、USB 操作、私有数据读取；不改 WordPress DNS；不启用 GitHub Pages；不自动发布/合入到 main；不修改 Draftor/bgIME 运行逻辑。**

代码只在隔离分支和本地进行，完成软件验证后停止。真实设备验收及网站上线是后续独立阶段，需用户明确授权。

如果标准 ESP Web Tools / esptool-js 无法保持现有安装器的安全合同，不要降低产品安全目标以「完成网页烧录」；应明确标记阻碍，并保留已经完成的网站部分。
