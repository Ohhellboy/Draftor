# 下一阶段：微雪专用测试设备连续动作单

**本轮没有执行本文件。** 需后续一次明确授权后连续完成本套动作；中途按停止条件处理，不逐步重复申请普通实施许可。不得以生产设备验证 fresh。

范围：准确 `v0.1.0-alpha.3` App 的兼容更新。真实 fresh 继续锁定；全片擦除接口需独立修订与空板资格验证，不夹带在本动作中。

1. **准备可恢复现场。** 只使用已核对实物为 WAVESHARE_RLCD42 / ST7305 的专用测试板。保留准确旧 App、原分区/OTA，以及已核验的完整 16 MiB Flash 备份；确认恢复工具、同板身份与原始偏移可用。私下保留 NVS/配对、TF 文稿、学习目录及重要正文导出。既有有效备份可复用；截断备份、只有旧 App 或只勾确认框均不足。记录测试前已配键盘、保存状态与可复核文稿。
2. **安全进入 ROM。** 保存文稿，正常结束 USB 传输并弹出；彻底断电（注意电池），取出 TF，断开其他开发板。按住 BOOT 接 USB，约两秒松开。关闭所有占用串口的应用，不切换 DTR/RTS，不加载 stub。
3. **先做对照，只读。** 在私有新目录运行准确发行 Python 安装器 `--mode update` 的默认只读计划，使用 esptool 5.3.1、明确端口、之前核验的预期 MAC、`--no-stub --before no-reset --after no-reset`。保存实际 4096 字节 partition、8192 字节 OTA 和安全/Flash-ID 结果。结束 Python 串口会话，不重置设备。
4. **核验浏览器读取。** `npm run build` 后在 localhost 运行默认锁写站点。手动输入同一私人 MAC、确认实物、选择唯一对应 USB Serial/JTAG 端口。先确认安全信息、16 MiB、固定 B 分区和活动槽与 Python 对照一致。开发者检查应答长度、ROM 慢读内容及 MD5 交叉校验是否可靠，记录耗时；日志只存私人测试目录。发现任何差异就停止，不解锁写入。浏览器关闭后没有自动重启；必要时按第 2 项人工重新进入 ROM。
5. **一次兼容更新。** 使用 `npm run build:device-test` 生成 `dist-device-test`，另以 localhost 启动。再连接同一板，核对新的只读计划。勾选已核验的可恢复备份、TF 已取出、完整计划确认；有准确旧 App 时选择该文件作附加本地比对。执行一次更新：计划若为 app0 只能写 `0x10000`，若为 app1 只能写 `0x410000`。应无全片擦除、无非 App 文件写入、无重试/重置，直到独立内容校验和保护区域检查后出现 `VERIFIED_BOOT_PENDING`。
6. **独立核验与启动。** 关闭浏览器串口，用发行 Python `verify-flash` 对同一真实活动偏移核验准确 App，并对照写前完整备份核验活动槽外字节、分区、OTA 和配对区域。私下保存结果；不要上传 MAC、Flash、NVS 或配对材料。完全断电，按本地 TF 指南核对词库、字体、`relations.bgr` 和 `relations.hnv`，插回卡、松开 BOOT 普通启动。用原键盘原信道唤醒，验证中文/英文输入、保存状态、既有文稿及学习记录；重启后再检查保存内容。
7. **覆盖另一个活动槽并结案。** 如已有可恢复、合法 OTA 状态预置的另一块测试板/测试基线，对另一个活动槽连续重复第 2–6 项。不得为了凑覆盖率临时猜改 OTA 或强写未知槽；没有对应现场则明确留作 `DEVICE_PENDING`。归档浏览器版本、OS、实际芯片/Flash/安全应答、慢读时长、计划/回执、Python 对照及启动验收。只有真实通过的项目改为 DEVICE_PASS；软件模拟不能替代。

**任一阶段停止条件：** 无完整可恢复备份、板型/身份不符、安全状态未知或启用、非 16 MiB、非 JTAG 路径、分区不符、OTA 模糊/pending/rollback、ROM 读数据或独立摘要不符、超时/断线/任何 I/O 错、槽外变化、非计划写入、保存/启动/配对异常。保留当时状态与私人证据，不自动重刷，不改走 fresh，不换槽，不擦除，不强制重启。写入中断可能导致活动 App 不完整，恢复动作必须依据已经核验的同板备份。

本套不在正常更新中故意拔线。破坏性断电恢复试验需要另外明确纳入专用可恢复测试现场；本轮软件已覆盖相应失败回执和停止逻辑。
