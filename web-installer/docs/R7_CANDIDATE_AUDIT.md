# R7 public-install candidate audit

Review-only source; never deployed to Pages. The live artifact remains the independent ReadOnlyDriver build at source aa8a6014b42af10c9aba14ed3aba25f879d758b5. No R7 physical USB connection or Flash operation is authorized or performed by these tests.

The original S3Rom and InstallSession two-flag mutex remains. Candidate construction requires both legacy write flags false. S3Rom grants a single mode once, after independently rechecking identity, partition/OTA slow reads versus ROM MD5, metadata SHA-256, full-device backup MD5, and either exact Alpha 3 app0 content or the pinned factory fingerprint. Reservation happens before asynchronous work; failure is terminal. No transport, SLIP parser, retry, stub or reset layer was added.

The session initially binds the selected USB identity after chip/capacity/security validation. Candidate app1 and unknown current App images stop. Proven blank Flash produces a read-only fresh plan but never a hardware capability. Exact factory NVS/phy variation is accepted only within the existing R6 pinned mutable range; the code, table and entire tail remain fingerprinted.

A local full backup may be captured read-only or supplied as an existing file. A download click does not establish backup proof. The saved 16 MiB file must be reopened, match full-device ROM MD5 and, following capture, SHA-256. The proof is private and bound to the current session. Before writing, identity, metadata, original content and backup digest are checked again. Capture failure, disconnect, mismatch or cancellation stops. Receipts record the verification outcome but not MAC, private hashes or Flash bytes. TF backup remains a separate user responsibility; the page never reads or writes TF.

Only after all gates does the existing writer run: update writes exact App bytes at app0, fresh separately confirms full 16 MiB erasure and writes the existing four fixed files. Existing post-write MD5, protected-range checks, partition/OTA readback, full initialized digest and no-auto-reset behavior remain. `VERIFIED_BOOT_PENDING` is never relabelled as normal operation.

Targeted tests cover the real ROM implementation against an independent synthetic USB device. Normal Chrome DOM flows include complete backup download, saved-file reimport, optional old App input retained, separate erase confirmation, update/factory success, app1/blank refusal and asset 404. These are software evidence, not new physical qualification.

PUBLIC_INSTALL_BLOCKED: the new ordinary-user recovery workflow has not been independently qualified; the candidate explicitly explains that recovery still needs the controlled Python 5.3.1 procedure and an experienced operator. No actual device read-only session has been executed from the public HTTPS origin under the new session/backup flow. R3 localhost and R4/R6 hardware evidence is inherited without claiming those new conditions passed. Windows/Edge hardware, mainland downloads, spare TF and UART0 status remain unverified. Do not repeat R3–R6 writes or factory restoration merely to inflate test coverage.

To reproduce software checks in the original workspace: `node --test tests/r7-candidate.test.mjs tests/r7-identity.test.mjs tests/r7-http.test.mjs`; `node tools/test-r7-ui.mjs`. The exact factory fixture is fetched/verified by the inherited `tools/fetch-factory.mjs`. Tests never enumerate OS ports. Build review candidate with `node tools/build-r7-candidate.mjs`; production locked publisher rejects it. The public and candidate source archives intentionally omit synthetic injection scripts; the separate local review test package supplies them.
